# API для внешних систем

Контур чтения для коннектора Aspro.Cloud и других служебных систем компании.
Закрывает пункты **9.1** (публичный REST API с версионированием) и **9.2**
(служебные ключи) из раздела Влада.

Документ написан так, чтобы по нему можно было подключиться, не заглядывая в код.

---

## Коротко

| | |
| --- | --- |
| Адрес | `https://<домен>/api/v1/<раздел>` |
| Метод | только `GET` — контур на чтение |
| Доступ | заголовок `Authorization: Bearer colz_…` |
| Формат | JSON, даты в ISO 8601 (`2026-10-09T12:00:00.000Z`) |
| Предел | 1200 обращений в час на ключ |

Записи в сервис через API **нет** намеренно: в задании сказано «передача из
Colizeum Agency в Aspro.Cloud, обратная синхронизация не требуется». Контур
только на чтение — это снимает целый класс рисков.

---

## Ключ

Ключ выдаёт администратор сервиса: **«Команда» → «Ключи для внешних систем» →
«Выпустить ключ»**. Указываются три вещи:

- **для кого** — название, чтобы потом было понятно, какой ключ отзывать;
- **что открываем** — список разделов; ключ открывает ровно отмеченное;
- **срок** — от 3 месяцев до 2 лет. Бессрочных ключей нет намеренно: забытый
  вечный ключ — это открытая дверь, про которую все забыли.

Вид ключа: `colz_<8 символов><32 символа>`. Первые 8 символов после `colz_` —
это префикс: по нему ключ видно в списке (`colz_7f3a…`) и по нему же его можно
опознать, если он случайно попал в чужой лог или репозиторий.

**Ключ показывается один раз.** В базе хранится только его отпечаток, как у
пароля, — показать значение второй раз физически неоткуда. Потеряли — выпускайте
новый, старый отзывайте.

### Замена без простоя

Живых ключей может быть несколько одновременно. Порядок:

1. выпустить новый ключ;
2. переключить на него внешнюю систему;
3. убедиться, что данные идут;
4. отозвать старый.

Отзыв действует сразу: следующий же запрос получит `401`. Отозванный ключ
остаётся в списке — по нему видно, что ключ был и когда его закрыли.

## Разделы

| Адрес | Что отдаёт | Соответствие в Aspro |
| --- | --- | --- |
| `/api/v1/advertisers` | Клиенты: название, реквизиты, подписант | CRM → Контрагенты |
| `/api/v1/deals` | Сделки: стадия, суммы, сроки, договор | CRM → Сделка |
| `/api/v1/documents` | Карточки документов (без файлов) | Документы |
| `/api/v1/tasks` | Задачи: название, срок, статус | Задачи |
| `/api/v1/invoices` | Счета: номер, основание, сумма | Счета |
| `/api/v1/tournament-contractors` | Контрагенты турнирного направления | CRM → Контрагенты |

## Параметры

| Параметр | По умолчанию | Что делает |
| --- | --- | --- |
| `limit` | 50 | Сколько записей на странице, максимум 200 |
| `cursor` | — | Продолжить с записи, чей `id` передан |
| `updatedSince` | — | Только изменённые после этой даты |
| `all` | — | `all=1` снимает отбор «помечено к передаче» |

### Постранично — курсором, а не номером страницы

Нумерованные страницы ломаются, когда во время перебора кто-то добавил запись:
часть строк показывается дважды, часть пропускается. Поэтому ответ содержит
`nextCursor` — его нужно передать в следующий запрос как `?cursor=…`:

```
GET /api/v1/advertisers?limit=100
→ { "data": [...], "nextCursor": "cmuy53wra000d7dfh", "hasMore": true, "total": 243 }

GET /api/v1/advertisers?limit=100&cursor=cmuy53wra000d7dfh
→ { "data": [...], "nextCursor": "...", "hasMore": true, "total": 243 }
```

Когда `hasMore` равно `false`, перебор закончен.

### Только изменённое

Сортировка всегда идёт по `updatedAt` по возрастанию — порядок устойчив, и
синхронизацию можно продолжить с того места, где прервались.

```
GET /api/v1/deals?updatedSince=2026-10-01T00:00:00Z
```

Обычный порядок работы коннектора: запомнить `updatedAt` последней полученной
записи и в следующий раз передать его в `updatedSince`.

### Что именно передаётся

По умолчанию отдаются **только записи, помеченные к передаче** (поле
`syncEnabled` в сервисе). Это сделано, чтобы в Aspro не уехало всё подряд,
включая черновики и внутренние пометки.

`?all=1` снимает отбор. Нужен в двух случаях: первая полная выгрузка и разбор
расхождений («почему у вас есть, а у нас нет»).

## Ответы

Успех — всегда одна и та же оболочка:

```json
{
  "data": [ { "id": "...", "updatedAt": "2026-10-09T09:12:00.000Z", "...": "..." } ],
  "nextCursor": "cmuy53wra000d7dfh",
  "hasMore": true,
  "total": 243
}
```

Ошибка:

```json
{ "error": { "code": "forbidden", "message": "Этому ключу раздел «tasks» не открыт" } }
```

| Код | Когда |
| --- | --- |
| `401` | ключ не передан, не найден, отозван или просрочен |
| `403` | раздел не входит в разрешения этого ключа |
| `400` | неверный параметр (например, `updatedSince` не похож на дату) |
| `429` | превышен предел обращений; в заголовке `Retry-After` — через сколько секунд повторить |

## Деньги: важное про НДС

В сервисе действует правило: **вводим чистую сумму, показываем с НДС**.
Поэтому поля названы так, чтобы их нельзя было перепутать:

- у сделок — `amountNet`, `contractTotalNet`: суммы **без НДС**;
- у счетов — `amountGross`: сумма **с НДС**, потому что её переписывают с
  настоящего документа, где она уже с налогом.

Ставка НДС зависит от даты документа (2025 — 20 %, 2026 — 22 %). Пересчёт — на
стороне принимающей системы, но знать об этом различии она обязана.

## Сопоставление записей

У каждой сущности есть поле `asproId` — место под идентификатор той же записи на
стороне Aspro. Сейчас оно пустое: заполнять его будет коннектор после первой
успешной передачи, чтобы потом обновлять, а не создавать дубль.

Рядом в сервисе живут `syncEnabled` (подлежит передаче), `syncStatus`
(`disabled` / `pending` / `synced` / `failed`) и `asproSyncedAt` (когда ушло
в последний раз) — они видны сотруднику в карточке.

---

## Что видно в сервисе

Каждое обращение по ключу пишется в **«Соответствие» → «Журнал действий»**:
какой ключ, какой раздел, сколько записей отдано, с какой даты. Отказы — тоже,
отдельной строкой. Наверху той же страницы, в блоке «Куда уходят данные»,
API стоит отдельным каналом со счётчиком за месяц.

В записи журнала попадают **категории** данных и количество, а не содержимое:
«ушли название и реквизиты организации, записей 13», но не сами реквизиты.

## Пример

```bash
KEY="colz_7f3a…"

# первая полная выгрузка клиентов
curl -s -H "Authorization: Bearer $KEY" \
  "https://<домен>/api/v1/advertisers?all=1&limit=200"

# ежедневная подкачка изменений по сделкам
curl -s -H "Authorization: Bearer $KEY" \
  "https://<домен>/api/v1/deals?updatedSince=2026-10-08T00:00:00Z&limit=200"
```

## Машинное описание и Postman

Текстовая инструкция выше — для человека. Для программ есть то же самое в
машинном виде:

| Адрес | Что это |
| --- | --- |
| `https://<домен>/api/v1/openapi.json` | Описание OpenAPI 3.0: адреса, параметры, все поля с пояснениями |
| `https://<домен>/api/v1/postman.json` | Готовая коллекция Postman: 12 запросов на все разделы |

Оба открываются **без ключа**: данных они не содержат, только список адресов и
названия полей — то же, что в этом документе. Требовать ключ, чтобы прочитать
инструкцию, значит мешать тому, кто подключается.

**Postman:** File → Import → вставить адрес `…/api/v1/postman.json`. Затем в
переменных коллекции задать `baseUrl` (адрес сервиса) и `apiKey` (ваш ключ).
Дальше все запросы работают сразу.

**Генератор клиента:** по `openapi.json` собирается типизированный клиент на
любом языке — это экономит день работы над коннектором.

> Описание строится из того же списка, по которому API отдаёт данные. Поэтому
> «в описании одно, а приходит другое» здесь невозможно: добавили поле — оно
> появилось и в выдаче, и в описании. На стороне сервиса это дополнительно
> проверяется командой `npm run api:check`.

## Чего пока нет

- **Webhook'и** (пункт 9.3) — **отложены осознанно, до переезда на серверы
  компании.** Сервис не оповещает о событиях сам: коннектор забирает изменения
  по `updatedSince` с любой нужной частотой, и «передача при создании и
  изменении» этим закрывается. Webhook'и дают мгновенность без опроса — это
  улучшение, а не условие работы.

  Почему не сейчас: гарантированная доставка с повторами и «мёртвой очередью»
  требует постоянной очереди (Redis или RabbitMQ) и отдельного рабочего
  процесса. Сегодня сервис — один процесс с базой-файлом, и такая схема по
  определению гарантий не даёт. Выбор очереди и присмотр за ней — решение
  того, кто управляет серверами; сделать это на временной машине значит
  переделать потом заново.

  Коннектор можно писать уже сейчас: когда webhook'и появятся, они подключатся
  к нему без переделки — список сущностей и событий тот же, подпись считается
  тем же ключом.
- **Тестовый контур** (пункт 9.5) — отдельная база для отладки коннектора.
- **Запись в сервис** — по заданию не требуется.

Версия контура — `v1`. Если формат придётся менять несовместимо, появится
`/api/v2`, а `v1` продолжит отвечать, пока коннектор не переедет.
