# Colizeum Agency — проект

Внутренний сервис менеджера рекламных проектов COLIZEUM: **CRM + документы с версионированием + календарь размещений + финансы + ОРД + промокоды + база знаний + журнал**.

Исходное ТЗ — `docs/Colizeum_Workspace_БЛУПРИНТ_v2.md`; поверх него выполнено большое ТЗ на доработку (см. «Текущее состояние»). Читай блупринт при работе над доменной логикой.

## Про пользователя

Пользователь — не программист. Объясняй просто, по-русски. Работай маленькими шагами: один блок → короткое резюме → подтверждение. Не выдумывай доменные данные (реквизиты, цены, документы) — только то, что дал пользователь.

Ячейки загрузки стоят в карточке сделки (счета, медиапланы, документы), в креативах клиента, в «Документах» и в карточках базы знаний. Поля `advertiserId`/`dealId` заполняются при загрузке — файл из сделки виден и у клиента. Поддержано перетаскивание мышью.
- **Обзор отдела**: воронка укрупнена до 6 шагов (Лид → КП → Договор → Подписание → Размещение → Закрытие), клик раскрывает контрагентов с менеджером, суммой и сроком; виджеты «блокеры / просроченные / зависшие» раскрываются в списки (`DeptFunnel.tsx`).
- **«Сегодня»**: порядок — цифры → «Решения, которые ждут вас» → поручения руководителя → задачи/блокеры → кольца стадий → статус дня.
- **Дневник** — под транскрипты встреч: тип записи, «с кем встреча», клиент, вставка расшифровки и прикрепление файла записи. **Показатели встречи** (дата, начало, окончание, продолжительность шагом 0,5 ч, участники, ссылки на протокол и на встречу, итоги) заполняются кнопкой «Разобрать транскрипт» (`/api/journal/parse-meeting`, ИИ) и при сохранении уходят строкой в Google-таблицу отчётности — `src/lib/services/meeting-sheet.ts` + скрипт-приёмник `deploy/google-apps-script.gs` (колонки сопоставляются ПО НАЗВАНИЯМ в шапке листа, ключи Google не нужны; установка — `docs/MEETINGS_SHEET.md`). Не настроено — кнопка «Отправить в таблицу» копирует готовую строку в буфер.
- **Блокер сделки** — флажок + комментарий (`Deal.blockerActive`): сводки считают блокером только поднятый флажок, снять можно одним кликом (`BlockerToggle`). Свободные тексты сделки очищаются пустым полем (`clearableString` в validation) — раньше пустая строка оставляла сделку «заблокированной» навсегда.
- **Вопрос руководителю** — заметный виджет на «Сегодня» с вложениями прямо в форме (`DecisionRequest.attachmentsKey` → `FileAsset` с `ownerType="decision"`).
- **Прод-деплой** — `deploy/` (setup-server.sh, nginx, pm2, update.sh, backup.sh) + пошаговая инструкция `docs/DEPLOY.md`: Timeweb DNS → AdminVPS → HTTPS.
- **Файлы базы знаний** (`KnowledgeFile`, `/api/knowledge/files`): блок «Файлы и шаблоны» на `/knowledge` — загрузка/скачивание договора, прайса, презентации через StorageProvider (ключи `knowledge/{id}/…`).
- **Поручения руководителя**: Director ставит задачу сотруднику (`Task.assignedById`, `/api/leadership/tasks`, кнопка «Поручить» в обзоре и на карточке сотрудника); у сотрудника — бейдж «🎯 Поручение» на доске задач.
- **Запросы юристу и на размещение** (`src/lib/request-templates.ts`, кнопки `deals/RequestButtons.tsx` в карточке сделки): две формы по порядку работы — сначала «Запрос юристу» (договор и спецификация), потом «Запрос на размещение» (макеты в клубе). Галочками отмечаются рекламные форматы (`AD_FORMATS` в enums — список дал пользователь, не выдумывать); реквизиты клиента, номер договора, суммы и сроки подставляются из карточки. Ничего не сохраняется в базу: форма выдаёт готовый текст, его правят руками и копируют в письмо. Три подсказки от домена: у форматов с `needsOrd` в текст добавляется блок про ЕРИД; если у клиента пусты ИНН/адрес/подписант — предупреждение до отправки; если сделка не дошла до предоплаты — предупреждение, что размещать рано. ⚠️ Формулировки — черновик по правилам из базы знаний, образцов от юриста не было; правятся прямо в `request-templates.ts`.
  - **Запрос юристу**: даты периода — календарём; сумма вводится ЧИСТОЙ, с НДС досчитывается сама по ставке из даты договора (`vatRateForDeal` → `withVat`) и уходит в текст тремя строками (с НДС / в т.ч. НДС / без НДС); выпадающие списки — `GEO_OPTIONS` (все клубы РФ / Москва и МО / другое), `CREATIVE_OWNERS` (кто делает макеты), `ERID_OWNERS` (кто получает маркировку — поле включается, только когда выбран интернет-формат), `SIGNING_OPTIONS` (ЭДО / бумага), `PAYMENT_SCHEMES` (100 % предоплата / 50-50 / другое). Поля «к какому сроку нужен документ» нет — убрано по просьбе пользователя.
  - **Два приложения**: галочка «Отдельное приложение под интернет-форматы» появляется, когда среди выбранного есть `needsOrd`, и разносит текст на «Приложение № 1 — размещение в клубах» и «Приложение № 2 — интернет-размещение (с маркировкой ЕРИД)» (`clubFormats` / `internetFormats`).
  - **Запрос на размещение**: под каждым выбранным форматом — своё поле ссылки (`links: Record<формат, ссылка>`), потому что в кликабельные баннеры вшивается UTM клиента, а в статичные — ссылка под QR-код; ссылка печатается строкой под своим форматом. Даты тоже календарём.
- **Хронология по клиенту** (`src/lib/services/client-timeline.ts`, компонент `advertisers/ClientTimeline.tsx`, типы — `src/lib/timeline.ts`): единая лента в карточке клиента — сделки, встречи из дневника, статусы дня, задачи, версии документов и файлы, оплаты, размещения, ОРД. Восемь типов событий с фильтрами и группировкой по дням; будущее (плановые платежи, сроки, запуск) вынесено в свёрнутый блок «Впереди», чтобы стена планов не закрывала историю. Кнопка «Пересказать историю» → `/api/ai/timeline-summary` (последние 150 событий в промпт). ⚠️ История изменений в базе не пишется (стадии сделки не логируются) — лента строится из дат, которые реально записаны: создание, дата договора, дата оплаты, дата загрузки.

**Заявки с сайта** (`/leads`): поток обращений из формы на colizeum-agency.ru. Тянутся из рабочей Google-таблицы CSV-экспортом (`src/lib/services/leads-sync.ts`, разбор — `src/lib/leads-parse.ts`; ключи Google API не нужны, но таблице нужен доступ «по ссылке — Читатель»). Синк при открытии страницы (не чаще раза в 3 мин) + кнопка «Обновить» (`/api/leads/sync`). Дедуп по `requestid` формы (`Lead.externalId`). Статус/ответственный/заметка живут в CRM и синком не перетираются (`/api/leads/[id]`). Раздел общий для всех сотрудников (без гейтинга по `track`).

**Мессенджер** (`/messenger`): каналы (Channel, «Общий» неудаляемый), сообщения (ChatMessage: закрепление, привязка к клиенту/сделке через денормализ. context), вложения (ChatAttachment через StorageProvider, ключи `chat/{channelId}/{messageId}/…`), поллинг ленты ~4с. Общий для всех сотрудников.
**Команда** (`/team`): админ (Owner) создаёт доступы и правит имя/роль (PATCH `/api/users/[id]`). Здесь же:
- **Личная таблица учёта** (`User.sheetUrl`): раньше адрес таблицы был один на всех в `.env`, теперь ссылка живёт у сотрудника — каждый ставит свою, админ может поправить любому. Из ссылки разбирается id таблицы **и gid листа** (`src/lib/sheet-url.ts`) — учёт часто ведут не на первой вкладке. Таблице нужен доступ «по ссылке — Читатель» (ключи Google API не нужны). Заявки с сайта на это не завязаны: там таблица общая, из `.env`.
Календарь отпусков живёт не здесь, а в «Передаче дел» — см. ниже.

**ИИ** (`src/lib/ai.ts` — единый шов). Провайдер выбирается в `.env` строкой `AI_PROVIDER`: `deepseek` и `yandex` — проверено доступны из РФ (у пользователя Qwen и Kimi режет провайдер интернета: ECONNRESET); `qwen`/`kimi` — OpenAI-совместимые; `anthropic` — Claude (из РФ отвечает 403 «Request not allowed»); `openai` — любой другой совместимый сервис. Ключ — `AI_API_KEY`, модель — `AI_MODEL` (по умолчанию qwen-plus / moonshot-v1-32k / claude-sonnet-5), адрес — `AI_BASE_URL` (подставляется по провайдеру). Инструменты напарника — `src/lib/ai-tools.ts`, типы `AiTool`/`AiMessage` нейтральные, поэтому смена провайдера кода не касается. Ошибки провайдера переводятся в человеческий текст (`aiErrorMessage`).

**Передача дел** (`/handover`, `Handover` + `HandoverItem`): сотрудник уходит в отпуск — выбирает своих клиентов, кому передать и до какой даты. Кнопка «Собрать саммари» (`/api/handover/preview`) готовит текст по каждому клиенту: где работа, что подписано и оплачено, что горит, блокеры и сроки — факты собираются из базы (`src/lib/services/handover.ts`), ИИ только пересказывает; без ключа ИИ саммари всё равно формируется списком фактов. Отправка меняет `Advertiser.ownerId` на замещающего и запоминает прежнего владельца в `HandoverItem.previousOwnerId`; «Вернуть дела» ставит всё обратно. Принимающему уходит уведомление.

Сверху на той же странице — **календарь отпусков** «Кого не будет на месте» (`Absence`, `/api/absences`, компонент `handover/VacationCalendar.tsx`). Типы — отпуск / больничный / командировка / отгул, у каждого периода поле «кто подхватывает дела» (`coverUserId`). Порядок блоков не случаен: сначала «кого и когда не будет», потом «кому уходят клиенты» — отпуск планируют раньше, чем передают дела. Своё отсутствие ставит каждый, чужое — руководитель или админ; календарь виден всей команде.

⚠️ Календарь переделан после жалобы «неоднозначно большой, недельные отпуска теряются, непонятно что за числа». Была годовая сетка «сотрудники × 48 недель»: недельный отпуск занимал одну клетку, чисел на сетке не было вовсе, а на полосе стояло имя замещающего — и читалось так, будто уезжает он. Теперь три блока сверху вниз: **«Сегодня»** (кого нет прямо сейчас, до какого числа, у кого дела) → **месяц по дням** (в шапке числа и дни недели, выходные притенены, сегодня подсвечен; клик по клетке заводит период с этой даты; полосы обрезаются по краям месяца стрелками ← →) → **список словами** «Впереди» с точными датами и длиной в днях. На полосе пишем ТИП отсутствия, замещающего — только словами «дела у Кати».

**Правки по итогам тестирования (08.2026):** тип сделки «Прямой клиент»; статус дня поднят наверх «Сегодня»; архив отвеченных вопросов (`DecisionRequest.archivedAt`); файл карточки контрагента; задача «Связаться с …» заводится сама, когда у заявки появляется ответственный. **Задачи**: примечания убраны с карточки (значок 💬, текст по клику), приоритет `Task.priority` полосой слева, перетащенная карточка встаёт первой (`Task.movedAt` + сортировка), файлы к задаче, клиент выбирается первым полем и его название уходит в начало заголовка. **Дневник**: длинная расшифровка свёрнута до трёх строк. **Меню профиля** (`src/components/UserMenu.tsx`): фото, смена пароля, выход — по клику на аватарку. **Документы**: в одну карточку кладётся несколько файлов (FileCell рядом с версиями) — версии остались для правок одного документа. **Предупреждения при смене стадии**: кроме «Знаю, принимаю» есть «Уточню к дате» — заводит задачу с дедлайном, стадия не меняется. **Сверка сумм в карточке сделки**: договор / разложено по месяцам / выставлено / оплачено, всё с НДС 22 % и чистой суммой подписью; расхождение с календарём платежей подсвечивается. **Единый вид денег.** Правило пользователя, одно на весь сервис: **вводим ЧИСТУЮ сумму (медиапланы приходят чистыми), показываем С НДС крупно и чистую подписью**. Ввод — `src/components/ui/NetAmountInput.tsx` (поле + живой пересчёт «с НДС 22 % — 122 000 ₽»), стоит в новой и в редактируемой сделке и в плановом платеже. Показ — `src/components/ui/Money.tsx`: `Money` (сумма с НДС крупно + «без НДС ≈ …»), `NetHint` (только подпись), `toGross` (для узких клеток, где рисуется своя цифра). Ставка по дате документа (`vatRateForDate`), не прибита гвоздями.

⚠️ **Исключение — счета и платёжки**: их сумму переписывают с настоящего документа, где она уже с НДС, поэтому там `vatIncluded` = true и подпись вычитает НДС, а не прибавляет. Из-за этого сверка сумм в карточке сделки приводит всё к виду «с НДС»: договор и календарь платежей домножаются (`contractGross`/`scheduledGross`), счета и оплаты берутся как есть.

⚠️ `Deal.vatIncluded` — легаси-пометка для записей, заведённых до правила (в форме был флажок «Сумма с НДС», включённый по умолчанию). Новые сделки всегда пишутся с `vatIncluded: false`. Разобраться со старыми — `npx tsx scripts/money-net-rule.ts` (показывает обе трактовки; `--fix-flag` правит только пометку, `--convert` пересчитывает цифры).

**Дорожная карта:**
1. ✅ Задачи от руководителя.
2. ✅ ИИ-кнопки в карточках (1A): «Саммари клиента за месяц», «Драфт ДС по шаблону». Нужен `ANTHROPIC_API_KEY`.
3. ✅ Внутренний мессенджер: каналы, **личка (DM)**, вложения, закрепы, привязка к клиенту/сделке, **мгновенный realtime (SSE, `src/lib/chat-events.ts` + `/api/chat/stream`)**.
4. ✅ ИИ-чат ассистент (1B) `/assistant`: чат с инструментами (`aiChat` в `ai.ts` — tool-loop; `/api/ai/chat`). Общий пункт меню.
5. ✅ **Напарник-картотека**: инструменты вынесены в `src/lib/ai-tools.ts` — читающие (list_my_clients, get_client, search_knowledge, list_inbox_files) и **пишущие** (route_file, create_task, add_daily_status, add_journal_entry, ask_leader). В чат можно прикрепить файл: он падает в «Входящие» (`FileAsset.ownerType="inbox"`, `/api/ai/inbox`), напарник определяет клиента/сделку и раскладывает через route_file — файл сразу виден в карточке сделки и в «Документах». Всё в скоупе сотрудника.

**Что напарник знает о сервисе** (правка после жалобы «плохо ориентируется»): в системный промпт `/api/ai/chat` подставляются два блока. `SERVICE_MAP` (`src/lib/ai-service-map.ts`) — карта сервиса обычным русским языком: разделы и что в них лежит, 9 стадий сделки, раскладка документов по 8 подразделам, глоссарий (ЕРИД/ОРД/ДС/УПД), незыблемые правила. Файл рассчитан на чтение человеком — правьте его, когда меняется структура сервиса. `buildAiContext` (`src/lib/ai-context.ts`) — шапка разговора: кто сотрудник, его роль, **сегодняшняя дата по Москве** (без неё напарник не мог посчитать срок «на завтра»), клиенты, сделки по стадиям, блокеры, счётчики задач и неразобранных файлов. Итого системный промпт ≈5,7 КБ.

**Руководство для напарника** (`src/lib/ai-manual.ts`, инструмент `read_manual`): 14 глав, ~22 КБ — как разговаривать, клиенты и сделки, 9 стадий по отдельности, документы и раскладка, разбор входящих файлов, задачи и сроки, деньги/НДС, ОРД, форматы и техтребования, промокоды, встречи, вопросы руководителю, кто за что отвечает, профиль компании. **В системный промпт уходит только оглавление (~0,8 КБ)** — главы напарник вытягивает инструментом по мере надобности: длинный промпт и дорог, и размывает внимание модели. Разделение источников: `read_manual` — как РАБОТАТЬ (порядок, правила), `search_knowledge` — ДАННЫЕ агентства (цифры, реквизиты, размеры). Фактура глав взята из базы знаний отдела и блупринта — не дописывать туда придуманное, напарник считает этот текст истиной. Итого системный промпт ≈7,4 КБ.

**Видно, куда напарник заглядывал**: `aiChat` возвращает `{ text, steps }` — список вызванных инструментов. Под ответом в `/assistant` рисуется «Смотрел: база знаний: «цены» → карточка клиента: МТС», а если инструментов не было — жёлтое предупреждение «Ответил без обращения к данным сервиса». Тот же след печатается в консоль dev-сервера (`[напарник] Имя: «вопрос» → …`). Это диагностика на случай жалоб «плохо ориентируется»: сразу видно, смотрел ли ИИ в данные или сочинял. Описания шагов по-русски — `describeToolStep` в `ai-tools.ts`.

⚠️ **Температура** (`AI_TEMPERATURE`, по умолчанию 0.2): у провайдеров по умолчанию 1.0 — режим свободной беседы, из-за которого напарник выдумывает клиентов и суммы. ⚠️ **`deepseek-reasoner` не поддерживает вызов инструментов** — с ним напарник перестанет видеть данные сервиса; для DeepSeek нужен `deepseek-chat`.

⚠️ **Поиск по базе знаний** (`search_knowledge`) считает в памяти, а не запросом в SQLite: `contains` у SQLite регистрозависим для кириллицы, из-за чего «цены» не находили статью «Цены» и напарник получал «ничего не найдено» на существующий контент. Теперь: нормализация регистра и «ё», отсечение окончаний только у слов от 6 букв (короткие ЕРИД/ОРД/ДС не режем — огрызок ловил мусор), вес заголовка ×3, при промахе отдаётся оглавление базы вместо пустоты.

⚠️ **Регион:** прямые запросы к Anthropic из РФ отвечают `403 Request not allowed` — ключ рабочий, блокируется адрес. Обход: сервер за рубежом, шлюз через `ANTHROPIC_BASE_URL`, или другой провайдер. Ошибки провайдера переводятся в человеческий текст (`aiErrorMessage` в `ai.ts`).

**ИИ-провайдер:** пока Claude (по решению пользователя — «прикрутить к тебе, позже переключим»). Обвязка провайдер-независимая через `ai.ts`. Открытые вопросы на будущее: (1) важна ли data-residency РФ; (2) какой провайдер вместо Claude.

**НЕ сделано (следующие итерации):** RBAC + аудит-лог, S3, realtime на несколько инстансов (сейчас in-memory, для 1 сервера), турнирные инструменты для ИИ-ассистента (пока видит только рекламный контур). **Ждём от пользователя:** `ANTHROPIC_API_KEY` в `.env` для всех ИИ-функций; база знаний коллеги.

⚠️ **Данные:** `npx prisma db seed` ОЧИЩАЕТ базу (демо-набор заново). После первого запуска на реальных данных использовать только `npx prisma db push` (сохраняет данные, добавляет схему).

**Проверка ИИ:** `npm run ai:scan` — показывает, до каких провайдеров достаёт сеть (ключи не нужны). `npm run ai:check` — делает один тестовый запрос к провайдеру и печатает вердикт (что настроено, куда ушёл запрос, что ответил провайдер). Быстрее, чем гадать через интерфейс.

## Боевой запуск на домене

Инструкция — `docs/ДЕПЛОЙ.md` (писалась для непрограммиста, по шагам). Схема: обычный VPS (Ubuntu 24.04) + Node 22 + pm2 + nginx + certbot. **Не serverless**: SQLite, локальное хранилище файлов и in-memory SSE требуют постоянного диска и одного процесса. Обновление сервиса — `scripts/deploy.sh` (бэкап → git pull → `prisma db push` → build → `pm2 restart`; сид намеренно не входит). Резервные копии — `scripts/backup.sh` по cron: база и `storage` живут только на сервере, из GitHub их не восстановить. В nginx критичны два места: `client_max_body_size 50m` (иначе не грузятся документы) и отдельный блок для `/api/chat/stream` с `proxy_buffering off` (иначе рвётся мгновенный чат).

**Скорость.** Замер (`deploy/perf-check.sh домен.ru`) показал: сам рендер страниц 12–37 мс на демо-данных — код не тормозит, тормозит окружение. Четыре места, где это лечится: (1) **SQLite в WAL** — по умолчанию база живёт в `journal_mode=delete`, где любая запись блокирует ВСЕХ читателей; режим включается один раз при старте (`src/lib/prisma.ts`, хранится в самом файле базы, переживает перезапуски). ⚠️ `backup.sh` из-за WAL копирует ещё и `-wal`, если `sqlite3` не установлен. (2) **HTTP/2 в nginx** — без него браузер тянет ~10 файлов страницы по очереди; включается параметром в строке, которую дописывает certbot: `listen 443 ssl http2;`. ⚠️ Отдельная директива `http2 on;` есть только с nginx 1.25, а в Ubuntu 24.04 идёт 1.24 — с ней сервер не стартует. (3) **`staleTimes` в `next.config.mjs`** — страница, открытая меньше 15 с назад, при возврате берётся из памяти браузера; 15 с намеренно мало, чтобы устаревших данных на экране не было. (4) **Мессенджер** больше не опрашивает сервер каждые 4 с поверх живого SSE-соединения: пока связь есть — раз в 20 с, во вкладке в фоне не опрашивает совсем.

## Архитектура

- **Монолит**: Next.js 15 (App Router) + TypeScript + Tailwind.
- **БД/ORM**: Prisma + SQLite (dev) → PostgreSQL (prod). Все сущности и связи — `prisma/schema.prisma`. Enum'ы хранятся строками, источник значений — `src/lib/enums.ts`, валидация Zod — `src/lib/validation.ts`.
- **Файлы**: `StorageProvider` (`src/lib/storage/`), dev — локальный диск `./storage`; в БД только метаданные (sha256, версии). Файлы ОРД — ключи `ord/{id}/{kind}/…`.
- **Auth**: cookie-сессия (JWT `jose`, httpOnly), bcrypt, 2 аккаунта. `src/lib/auth.ts`.
- **Слои**: страницы (server components, Prisma напрямую) → клиентские островки (`src/components/**`) → API-роуты (`src/app/api/**`, Zod, `{ error: { code, message } }`) → сервисы (`src/lib/services/**`).
- **Инварианты стадий** — `src/lib/services/deal-stage.ts`: предупреждения → 409 → подтверждение `confirm=true`.

## Незыблемые правила домена

- Приложения Т-Банка согласуются строго по очереди.
- Правки после подписания при запрете правки тела → **ДС** (кейс Алабуга).
- Платежи по клубу на ИП нельзя через счёт УК.
- Размещение стартует только после предоплаты.
- НДС по дате документа: 2025 → 20 %, 2026 → 22 % (`vatRateForDate`).
